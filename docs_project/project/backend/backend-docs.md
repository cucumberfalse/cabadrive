# Backend Docs

## MVP Decision

No backend is part of MVP. Cabadrive is intentionally local-first and offline-capable after build.

## Data And Storage Model

- Content is bundled as static assets generated by the content pipeline.
- User progress is stored locally. The MVP implementation uses a localStorage-backed adapter; IndexedDB remains the planned upgrade if data volume or structured querying requires it.
- No server database, queue, or cloud sync in MVP.

## API Surface

There are no runtime network APIs in MVP. Data-processing scripts for ingest/validation/export are repository tooling, not user-facing backend services.

Current tooling:

- `scripts/validate-content.mjs` validates content mode, source hashes, exam config, category B fallback constraints, local question images, disclaimers, guide/vocabulary references, approvals, release exceptions, structured practice-source scope, strict Russian translation coverage, question-image metadata coverage, and Russian explanation alignment evidence. It reads Russian translations, Russian explanations, and question-image metadata from range shards, then checks that the monolithic compatibility indexes are fresh.
- `scripts/content-shards.mjs` owns the deterministic shard loader and generated-index writer for `content/translations/ru/*.json`, `content/explanations/ru/*.json`, and `content/image-metadata/question-images/*.json`. Run `node scripts/content-shards.mjs --write-indexes` after editing a shard, or `node scripts/content-shards.mjs --check-indexes` to detect stale generated indexes.
- `scripts/content-topic-guide.mjs` owns no-file-I/O validation for draft/published topic-study-guide data under `content/guide/topic-study-guide.*.json`, including coverage baseline freshness, topic structure, ticket answer explanations, vocabulary provenance, and draft-safe versus published strict coverage behavior.
- `scripts/official-documents-validation.mjs` owns no-file-I/O validation for the governed official-documents manifest under `content/official-documents/manifest.json`, including required source metadata, local archive paths, SHA-256 hash shape and injected local hash comparison, conversion notes, currentness/effective-status enum fields, exact-text validation enum status, raw evidence for lossy formats, and source-trace checks that current guide claims do not cite missing or not-current documents.
- `scripts/content-image-metadata.mjs` validates generated question-image metadata plus `content/validation/question-image-metadata.evidence.json`. The structural gate requires image-backed questions to have usage mappings, unique image paths to have metadata, fresh path/hash/question fingerprints, approved evidence, and answer-critical detail mappings. The optional full-quality gate rejects placeholder/baseline/source-image-frame metadata, generic source-image or answer-cue usage, low-confidence required details, and approved records without actual visual-review evidence.
- `scripts/content-explanation-alignment.mjs` validates complete question-card Russian explanation coverage plus `content/validation/ru-explanation-alignment.evidence.json`. It requires correct-answer rationales, wrong-answer rationales, fresh explanation fingerprints, image-detail references for image-backed questions, and structured visual-claim contradiction checks. The full-quality gate also rejects generic filler, Spanish residue, transliteration, and unsupported Latin residue.
- `scripts/content-translation-alignment.mjs` computes stable offline fingerprints for Spanish source tuples and Russian translation tuples, then validates approved local evidence under `content/validation/` so stale, missing, extra, or unaudited translation edits fail preflight without any network, LLM, or runtime service. The full-quality gate rejects draft wrappers, Spanish residue, transliteration, and unsupported Latin residue.
- `scripts/content-source-scope.mjs` owns the practice-source eligibility boundary. Practice questions must reference a source whose `practiceQuestionScope` explicitly allows the question category and uses an allowed scope kind. A/A4/motorcycle-specific source banks are rejected by structured scope, while motorcycle or motovehicle mentions inside valid category B material are allowed as shared-road topics.
- `scripts/generate-learning-support.mjs` is a deterministic local maintenance helper that regenerates the current image metadata/evidence, full translation coverage/evidence, and full explanation coverage/evidence from the current question bank and topic-guide answer rationales. It is not part of runtime and uses no network, LLM, OCR, or translation service.
- `scripts/sync-public-assets.mjs` copies committed content assets into Vite public assets before dev/build.
- `scripts/generate-service-worker.mjs` writes a production service worker with the built asset list for offline reload.

`pnpm run validate:content` is the structural offline validation used by build. `pnpm run validate:content:quality` enables the feature-009 hard gate and is expected to fail until every range shard is completed and reviewed.

## Official Documents Archive

Official source documents that support topic-guide claims are governed under `content/official-documents/`. See `docs_project/project/content-sources.md` for archive purpose, manifest fields, exact-text preservation rules, currentness/effective-status evidence, raw evidence requirements, and future-document rules.

## Deployment

Planned deployment shapes:

- Local Docker-served build for end-user study.
- Optional static hosting of build artifacts (while preserving offline behavior after first load).

## Future Backend Triggers

Backend should only be introduced with an explicit feature spec if requirements add multi-user accounts, sync, remote analytics, or managed content delivery.
