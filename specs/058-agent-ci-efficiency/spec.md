# Spec: Agent and CI efficiency

## Goal and boundary

Reduce idle agent turns and repeated full CI after final validation evidence is appended. Preserve the repository's existing quality and merge gates. This is one process/CI PR slice handed from Analyst to Architect on `codex/058-agent-ci-efficiency`, based on verified `origin/main` `9e17a059536586d8c2319f8cabcea9bcd288385d`. Parallel work may exist; preserve all sibling diffs, branches, commits, PRs, worktrees, and process memory.

## Scope

In scope: agent monitoring guidance, its relevant template mirrors, a narrow evidence-only classifier, step-level routing inside the existing `baseline-checks` and `docker-validation` jobs, provenance for a prior full run, and focused classifier tests. Out of scope: weakening any test, changing required check names or branch protection, skipping `guard`, `AI Review`, or `osv-scan`, changing product behavior, and treating ordinary Markdown/docs/spec edits as report-only.

## Requirements

- **FR-001 — Bounded monitoring.** Orchestrator owns CI/PR status monitoring. Agents use completion notification or one bounded wait when available; otherwise check once at a meaningful state transition, a planned decision point, or an explicit deadline, with backoff for a stuck run. Do not create a minute-by-minute status loop or duplicate status narration across agents. A timeout triggers a bounded check and recovery/escalation, not an assumption of success. Keep independent Review Agent and AI Review, ordered final Architect/Analyst validation, all current-head guards, and explicit gate checks immediately before merge.
- **FR-002 — Required checks remain actual checks.** On every PR head, `baseline-checks` and `docker-validation` jobs start and end with literal `success` only after their selected proof succeeds. Route at step level within those named jobs. Do not use workflow path filters, job-level skipping, `continue-on-error`, neutral/skipped conclusions, or a synthetic success status. `guard`, `AI Review`, and `osv-scan` continue independently. The finalizer's stricter literal `SUCCESS` requirement for all five names remains unchanged.
- **FR-003 — Full is default.** Full CI retains every current baseline and Docker step on PRs involving code, tests, content/data, assets, dependencies/locks, build/runtime/deploy files, any workflow or classifier/control code, agent rules/templates, new or changed requirements, plans, tasks, dispositions, or other semantic docs. This feature's PR itself always takes the full path because it changes CI and agent rules. Pushes to `main`, manual dispatches, unexpected events, forks with insufficient API access, and any uncertain classification take full verification or fail red; they never take the short path.
- **FR-004 — Narrow evidence format.** The short path is eligible only after an effective content commit `E` already exists on the same PR and every later commit changes only `specs/<one-feature>/feature-request.md` and/or `tasks.md`. In `feature-request.md`, only schema-valid Analyst bullets under the existing `## Final Analyst Validation Notes` may be appended. In `tasks.md`, only schema-valid Architect bullets under `## Final Architect Validation Notes`, an actual read-only current-head guard record under `### Final Validation Evidence`, and an optional factual PR status snapshot under `### Cycle PR Set` may be appended; all headings must already exist at `E`. The guard record must name `E`, the head actually checked, UTC time, result, and proof reference. A status snapshot must name the PR, branch, observed head, observed status/time, and final-validation inclusion without claiming a future outcome. Compare all original bytes and section boundaries for every intervening commit. Existing bytes, all other sections, headings, requirements, task checkboxes, dispositions, plans, and implementation notes must be unchanged. Added lines must match a finite, documented schema; freeform prose, instructions, new headings, deletions, replacements, renames, binary changes, whitespace rewrites, or malformed lines force full CI. The final guard must still be rerun externally on the actual latest head after any evidence commit.
- **FR-005 — Trusted effective-head proof.** Read `E` from the matching `Effective content head`, Architect-validated, and Analyst-validated markers, all equal to the same full SHA. Verify `E` is an ancestor of the exact current PR head, belongs to the same PR branch/repository, and every intermediate commit satisfies FR-004. Use a complete Git history/tree comparison; shallow, failed, truncated, or ambiguous data forces full CI. Do not trust a PR label, commit message, author claim, or file list from a PR event as proof.
- **FR-006 — Prior full-run proof.** A short run must find a prior GitHub Actions `CI` workflow run on this same PR branch/repository, triggered by `pull_request`, with `head_sha=E`, `conclusion=success`, and a completed successful `baseline-checks` and `docker-validation` job. Inspect GitHub's job-step data and require the known expensive baseline and Docker proof steps to have actually concluded `success`, including tests, build, browser smoke, Docker validation, and teardown; a skipped step is not proof. A machine-readable full-run record ties that run ID/attempt, `E`, PR number, base SHA, and CI workflow identity to the actual run. Current base SHA and workflow identity must match the record. Query GitHub with read-only `actions: read` permission and verify run/job/artifact identity from the API; PR-authored text or a downloaded artifact by itself is not authority. Missing, stale, mismatched, multiple conflicting, inaccessible, or failed proof forces full CI. In addition, any change from the trusted base to current head in workflow/classifier/control files forces full CI for the whole PR, even if a prior full run exists.
- **FR-007 — Current-head short proof.** If and only if FR-004–FR-006 pass, each required CI job runs a cheap, deterministic proof on the exact current PR head and reports successful short-path validation with machine-readable current head, `E`, base SHA, prior run ID/attempt, verified job-step conclusions, changed files, and classifier version. If proof fails unexpectedly, run the full suite or fail the required job red. The short path does not replace `guard`, `AI Review`, `osv-scan`, process-memory review, exact-head checks, or final validations.
- **FR-008 — Ready PR and merge.** Publish a ready-for-review PR with required Codex attribution. Run focused local checks and the full remote checks for this workflow-changing PR. Address AI Review and Review Agent findings, resolve review threads, record current process memory, complete Architect validation before Analyst validation, and verify all five required checks are `SUCCESS` on the exact final head. Once merge-ready, wait at least two minutes, then recheck head, checks, review, threads, conflicts, and process evidence. If readiness changes, restore it and restart the two-minute period. Orchestrator merges and verifies GitHub's merged state.

## Acceptance and negative scenarios

1. Agent rules have one monitoring owner and a bounded wait/backoff rule, with no lost review or final gate.
2. A fixture PR with a successful full CI run on `E`, unchanged base/workflow identity, and only schema-valid final evidence additions selects the short path; both required jobs execute proof and conclude literal `success` for the new head.
3. Any requirement/task/disposition change, non-append edit, unverified guard or fabricated/future PR status, arbitrary text in an evidence section, mixed/code/content/asset/lock/workflow/classifier change, missing or skipped prior step, missing artifact/API data, base drift, bad ancestry, shallow history, renamed/deleted file, wrong PR/repo/branch, or malformed marker selects full or fails red.
4. This feature PR demonstrably takes full baseline and Docker validation and retains successful `guard`, `AI Review`, and `osv-scan` checks. The exact final head is merge-ready with resolved threads; the two-minute delay and recheck precede merge.

## Evidence and sources

Record deterministic fixture results, short/full route decision output, prior-run API IDs and step conclusions, current-head check conclusions, independent review outcome, exact-head guard, final validation markers, and post-delay merge evidence in process memory. GitHub documents that path-filtered required workflows may remain pending and that skipped jobs can report success; this repository deliberately requires actual `SUCCESS`: [required status check behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks). GitHub's [workflow-run API](https://docs.github.com/en/rest/actions/workflow-runs) supports `head_sha` filtering; verify job steps via its jobs endpoint.
