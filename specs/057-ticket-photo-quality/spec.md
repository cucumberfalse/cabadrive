# Spec: Ticket photo quality (ТЗ-P3 stage 2)

## Goal and routing

Deliver source-faithful, reviewed, responsive ticket images for the existing 460-question fallback bank. This is the single Orchestrator-adopted slice on `codex/057-ticket-photo-quality`, based on verified main `3beb624c0c7c615ab7159fdd3227f74f790df29f`. Analyst intake is `feature-request.md`; Architect owns this spec, `plan.md` and task/disposition definitions. Implementation starts only after explicit Orchestrator assignment and all four artifacts exist. Parallel agents may exist; preserve every sibling file, environment, process, branch, commit, PR and process record.

## Scope

In scope: actual 15-image × three-model comparison, selected-model inference for all 275 canonical JPGs, individual visual review and rejected-only bicubic fallback, reviewed PNG masters and provenance, three-codec derivatives, all 276 reference joins, responsive ticket rendering, and the delivery/offline/static-retention changes necessary for those ticket URLs. Shared question cards cover learning, active/reviewed exam and mistakes. Materials/manual ticket references also render this same class-(c) corpus and must use the responsive ticket boundary with their existing captions/layouts preserved.

Out of scope: manual-page/crop regeneration, other raster-class UI migration, source-bank replacement, image synthesis, question/answer/explanation rewriting, complete stage-5 conversion, universal traffic claims, cache/worktree pruning, native dependency upgrades and unrelated process changes. Manual ticket references are in scope; manual illustrations and source figures are not.

## Requirements

- FR-001 Preserve canonical JPG bytes, paths and source attribution. Their existing question-image SHA-256 pins, question set/reference fingerprints, protected manuals and archives remain unchanged. The roadmap's pin task is fulfilled by verifying those unchanged pins and introducing separate enhanced-master/derivative pins; never bind a JPG pin to PNG bytes. Any unexpected original change blocks the slice.
- FR-002 Run the real `realesrgan-x4plus`, `realesrnet-x4plus` and `remacri` models on a fixed representative 15-image sample. Commit the sample IDs, selection rationale, actual per-model observations/metrics/output hashes, tool/model source identities and reproducible commands in `docs/improvements/priority/03-image-quality-decisions.md` and machine-readable evidence. A model name, example screenshots from another corpus, skipped inference or copied scores are not comparison evidence. Runtime/tool compatibility must be demonstrated by successful decoded ×4 outputs.
- FR-003 Perform selected-model ×4 inference for every unique JPG. Set aspect-preserving PNG master width to `max(1240, round(originalWidth * 2.2))`. Reduce genuine ×4 output to this width with `lanczos3` when possible. For originals narrower than310pixels (actual corpus minimum210), the ×4 output is below1240: explicitly enlarge that actual AI output to1240 using bicubic, record this additional interpolation and final effective factor, and subject the result to the same individual visual and sanity gates. This is additional delivery interpolation of actual AI pixels, not an original-image fallback or recovered factual detail. Do not repeat neural passes or claim every master is only2–2.3× original. The1240 delivery floor takes precedence over preferred scale; visually rejected results use FR-005 source fallback instead.
- FR-004 Individually inspect original and candidate for all 275 images, and explicitly classify every text/sign-bearing image. This stronger bounded inventory prevents heuristic omissions. Review source/output at matched display dimensions and critical regions at readable enlargement, comparing letters, numbers, arrows, road-user pose, geometry, colors, sign shapes and highlighted objects against canonical image metadata and usage relevance. Inspection means actual pixel viewing with recorded image-specific observations, reviewer identity and exact hashes; automatic flags/contact-sheet generation or one blanket approval cannot constitute review. Ambiguous details must remain ambiguous rather than being reconstructed as fact.
- FR-005 Only individually visually rejected AI candidates may use source-original bicubic (`sharp.kernel.cubic`) fallback to the same target dimensions. Journal status stays `rejected`, with concrete rejection reason, AI candidate hash/evidence, final fallback hash and fallback review. Accepted records must derive from actual selected-model inference. A failed metric alone is not an invented visual rejection; a metric failure requires actual investigation/review and disposition. Broad fallback without mandatory inference/review is incomplete stage 2.
- FR-006 Every final master, including rejected-case fallback, passes a separate upscale sanity gate: normalize both images to the same sRGB convention, reduce the master to the original's exact dimensions via `lanczos3`, and measure real DSSIM `<=0.02`. Retain original/final dimensions, normalization/kernel and actual score. Never enlarge the original for that comparison. Final derivative gates remain separately `DSSIM <=0.01` for every like-sized variant and hash-ranked sampled `SSIMULACRA2 >=70`.
- FR-007 Register exactly 275 class-`c` lossless PNG masters. A sorted reviewed journal joins canonical source path/hash, master path/hash/dimensions, accepted/rejected status, actual inference/model/binary identities and parameters, review evidence/hash, fallback reason where applicable and measured sanity score. The existing derivative `sourceSha256` continues to mean the PNG master, not its original JPG. Validation links that master identity back to the journal and canonical manifest. Bind reviews to source, selected model, processing policy and candidate/final hashes. Changed identity invalidates review; `--write` cannot fabricate/re-adopt an approval.
- FR-008 Preserve existing width inventory and add the explicit reachable per-source `targetWidth` to that source's variant-width set, deduplicated and sorted. Set ticket target width to 1240. Thus 480/800/1200 and 1240 are present for the usual masters; larger existing widths apply only when reachable. Every source has balanced AVIF/WebP/JPEG sets including a 1240 candidate. 1200 satisfies the stage's minimum but is 40 pixels short of 2×620; the explicit 1240 candidate closes that gap without changing the 620-CSS-pixel layout. Keep extension/decoded PNG/MIME, confined paths, no symlinks, complete inventories and metric identity gates.
- FR-009 Commit only this reviewed class-(c) PNG-master inventory despite the master-directory ignore (explicit scoped force-add is permitted). Every fresh checkout, CI and Docker context then has byte-identical approved inputs; AI inference is an explicit maintainer operation, never normal build/CI runtime. Missing/tampered originals, masters, evidence or derivatives fail validation. No network provisioning during ordinary validation/build and no empty-registry fallback. Keep model weights/binaries, QA caches, trial intermediates and masters outside public/dist/nginx payloads.
- FR-010 Ticket UI uses the existing typed `assetSrcSet` boundary: AVIF then WebP `<source>`, JPEG `src` and `srcSet`, container-correct `sizes` and positive intrinsic dimensions. Derive the 360-pixel height cap and aspect ratio from verified dimensions before load. Preserve alt text, question support controls, captions and percent-based overlay alignment; guard stale load events when tickets change. Canonical original remains the local fallback for absent manifest records, using known original dimensions wherever available. Production integrity validation rejects incomplete registry coverage rather than silently shipping absent records.
- FR-011 Implement bounded offline delivery: precache every ticket JPEG variant plus existing canonical assets, exclude ticket AVIF/WebP derivatives from install precache, runtime-cache successfully requested modern variants and map an unavailable modern ticket URL to its precached same-source/same-width JPEG. Map only integrity-checked local manifest URLs; keep unrelated requests and existing atomic install/update/navigation/retained-cache semantics intact. Verify an unvisited ticket at both tested DPRs works offline after initial ready install, not just an image already runtime-cached. An offline modern-source response must carry honest JPEG content type and tested browser decoding.
- FR-012 Serve hashed `/content/img/` assets with correct MIME, immutable success caching and actual404 on missing URLs. Preserve/package the complete append-only `assets-derived/img` inventory, including prior hashed files, in every subsequent Docker/static release so an old tab can fetch its old unvisited derivative after a new release. Existing pipeline keeps old outputs and sync copies the full directory; verify this actual behavior in a two-release test. This is packaged-history retention, not a claim that the stager's separate `/assets/` retained store already retains `/content/img/`. Do not delete/prune old derivative inventory; preserve legacy `/content/assets/` cache policy and outgoing legacy handoff. If the real upgrade tests reveal a delivery gap, return it to Architect before a broader stager redesign.
- FR-013 Record real elapsed batch/derivative/incremental times, original/master/derivative/evidence sizes, runtime and precache bytes, clone/git growth and disk peak. Resource planning is an execution gate, not an acceptance exception: provision locally owned tools, run a 15-image pilot, project the full batch and Docker peak against free disk with at least 2 GiB host headroom. Use sequential bounded work, small tiles and owned reusable intermediate files. No shared-cache, sibling, worktree or environment cleanup is authorized. Stop with concrete feedback if full scope cannot fit or execute.

## Review and final-validation contract

Review checks scope, actual review fidelity, licensing/tool-runtime separation, source provenance, responsive layout, offline/retained delivery and negative-case enforcement. Full preflight and Docker-only runtime commands remain mandatory; no host-wide installs. There is one cycle PR until Orchestrator explicitly creates another isolated latest-main slice.

Implementation feedback receives an Architect task/ticket or explicit not-needed disposition before completion. Architect validates all content, tasks, dispositions and customer intent; Analyst follows only after Architect PASS. Return limits are 10 Architect / 5 Analyst. Any non-evidence change after validation makes both validations stale. After freezing the effective content head, final role markers/cycle metadata/current-head guard notes may be appended as recognized evidence-only process changes; no recursive task-checkbox prerequisite may force a new behavior/content commit after every evidence commit. Orchestrator alone finalizes/merges with expected current head and all required checks, review/conversations, conflict, acceptance and guards satisfied. Cleanup is unassigned; preserve this active worktree.
