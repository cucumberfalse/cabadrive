## Контекст продукта и проблема

Cabadrive — статический local-first React/Vite тренажёр теории вождения CABA для русскоязычных пользователей; бэкенда нет, весь прогресс живёт в localStorage браузера. Потеря localStorage = полная потеря учебной истории пользователя.

Факты по текущему коду (проверены на base `3fed47cc`, номера строк актуальны — они сместились относительно цитат в ТЗ-P1 после мержей PR #208–#210):

- **Сброс всего прогресса — один тап без подтверждения.** Кнопка с иконкой RotateCcw в шапке (`src/App.tsx:5135-5143`, `aria-label="Сбросить прогресс"`) вызывает `reset()` (`src/App.tsx:5080-5082`), который делает `dispatchProgress({ type: "reset" })`. В store действие `reset` (`src/progressStoreCore.ts:427-437`) немедленно обнуляет состояние (`empty()`) и удаляет ключи `cabadrive.progress.v1`, `cabadrive.progress.v1.backup`, `cabadrive.progress.v1.recovery`. Ни confirm-диалога, ни undo, ни экспорта в UI нет (grep `confirm(` по `src/App.tsx` — 0 совпадений). Один случайный тап безвозвратно стирает все ответы, ошибки и попытки экзамена.
- **Store после PR #210 уже даёт готовую основу** (это и было причиной делать ТЗ-06 раньше слайса 1):
  - `dispatchProgress(action)` — единственная точка записи; действия включают `reset` и `importProgress` (`src/progressStoreCore.ts:46-51`; экспортируется из `src/progressStore.ts:38-40`).
  - `exportProgress()` возвращает канонический полный v2 JSON (`serializeProgress`, `src/progressStoreCore.ts:203-212`; обёртка `src/progressStore.ts:41-43`).
  - `importProgress` атомарен: строгая валидация `parseImportedProgress`/`strictV2` (`src/progressStoreCore.ts:214-234, 297-303`) — неизвестная version, битые вложенные записи, дубликаты aggregate отклоняют импорт целиком; `dispatch` возвращает `false`, состояние не меняется, поднимается recovery-событие `importRejected` (`src/progressStoreCore.ts:398-408`).
  - Recovery-события доступны UI через `subscribeProgressRecovery` / `getLastProgressRecovery` (`src/progressStore.ts:44-49`).
  - `mistakesFromProgress(progress)` — селектор ошибок (`src/progressStoreCore.ts:187-201`), уже используется в `StatusStrip` (`src/App.tsx:576-600`).
- **Данные для перечисления в модалке доступны без новых вычислений**: `progress.answers.length` (+ агрегат `prunedAnswerStats`), `mistakesFromProgress(progress).length`, `progress.examAttempts.length` — `useProgress()` уже подключён в App (`src/App.tsx:5027`).

## Цель

Ноль сценариев безвозвратной потери прогресса через кнопку сброса: сброс возможен только после явного информированного подтверждения, отменим до конца сессии браузера, а пользователь получает штатный механизм резервного копирования (экспорт) и восстановления/переноса (импорт) прогресса файлом JSON.

## Scope

В scope (три функциональных требования слайса 1 ТЗ-P1, уточнённые под текущий код):

- **FR-A1 (подтверждение сброса).** Тап по кнопке «Сбросить прогресс» открывает модальный диалог подтверждения, который перечисляет удаляемое в конкретных числах: N ответов, M вопросов с ошибками, K попыток экзамена (из `useProgress()`-состояния). Удаление выполняется только после подтверждения по схеме «текстовый ввод ИЛИ двойное подтверждение» (выбор конкретной схемы — за Architect; default-допущение ниже). Отмена/Esc/клик мимо не меняют данные.
- **FR-A2 (undo сброса до конца сессии).** Перед выполнением `reset` снапшот текущего прогресса (канонический v2 JSON из `exportProgress()`) сохраняется в `sessionStorage` (новый ключ). После сброса пользователю показывается тост/статус-панель с кнопкой «Вернуть»; нажатие восстанавливает прогресс из снапшота (через существующий строгий путь `importProgress`). Возможность undo живёт до конца сессии браузера (семантика sessionStorage). Если sessionStorage недоступен/переполнен — сброс после подтверждения всё равно возможен, но пользователь предупреждается, что отмена будет недоступна.
- **FR-A3 (экспорт/импорт прогресса JSON-файлом).** Кнопки экспорта и импорта рядом с кнопкой сброса (шапка приложения). Экспорт: `exportProgress()` → Blob → download с осмысленным именем файла. Импорт: выбор файла → чтение текста → `dispatchProgress({ type: "importProgress", raw })`; валидация схемы — существующая строгая store-валидация. Битый/чужой/устаревший JSON отклоняется атомарно: текущий прогресс не меняется, пользователь видит понятную ошибку (на базе recovery-события `importRejected`). Успешный импорт замещает текущий прогресс; так как импорт разрушителен для текущего состояния, он тоже проходит подтверждение и/или делает undo-снапшот (default-допущение ниже).
- Доступность диалогов по NFR-3 ТЗ-P1: фокус-ловушка, Esc, автофокус на безопасной кнопке; новые интерактивные элементы соответствуют текущим паттернам focus-visible и touch-таргетам ≥42 px (NFR-2).
- Тесты на новое поведение (unit при необходимости + e2e-сценарии AC-1 и негативного импорта) и прогон существующего e2e-набора в обоих проектах (NFR-1).
- Синхронизация durable-документации (`docs_project/`), только если фактическое поведение экранов/потоков изменяется в описанных там местах; отметка выполненности слайса 1 в чекбоксе плана `docs/improvements/priority/01-usability.md` — на усмотрение Architect (в предыдущих циклах статус-поля ТЗ не обновлялись — зафиксировать решение).

Вне scope:

- FR-A4, FR-A5, FR-A6 (персист экзаменационной попытки, guard-диалоги ухода, персист сессии обучения) — слайс 2+.
- Все требования групп Б, В, Г, Д, Е ТЗ-P1 (экзаменационный поток, закрытие ошибок, роутинг, поиск, тёмная тема, a11y-пакет).
- Изменение формата/схемы хранения прогресса, логики store, cap/quota/миграций — контракт ТЗ-06 реализован в PR #210 и не пересматривается; UI-слой только вызывает публичный API store.
- Слияние (merge) импортируемого прогресса с текущим — импорт замещает состояние (семантика store `importProgress`).
- Декомпозиция App.tsx (ТЗ-04), UI-библиотеки, новые зависимости.
- Синхронизация между устройствами, бэкенд, IndexedDB (ТЗ-15).

## Функциональные требования

1. Кнопка «Сбросить прогресс» никогда не вызывает `dispatchProgress({ type: "reset" })` напрямую — только через модальное подтверждение с перечислением удаляемых данных в числах (N ответов, M ошибок, K попыток экзамена).
2. Подтверждение защищено от рефлекторного клика: текстовый ввод либо двойное подтверждение (см. допущение A1).
3. Отказ от подтверждения любым способом (кнопка «Отмена», Esc, закрытие диалога) оставляет прогресс нетронутым.
4. Перед фактическим сбросом создаётся снапшот канонического v2-экспорта в sessionStorage; после сброса доступна видимая кнопка «Вернуть» (тост/статус-панель), полностью восстанавливающая прогресс; восстановление идёт через строгий import-путь store.
5. Undo доступен до конца сессии браузера; повторное нажатие «Вернуть» после успешного восстановления не задваивает данные (снапшот одноразовый или идемпотентный — детализация за Architect).
6. Недоступность sessionStorage не блокирует сброс, но пользователь явно предупреждается об отсутствии undo.
7. Экспорт скачивает JSON-файл с каноническим полным v2-состоянием (`exportProgress()`); файл, экспортированный на одном профиле, импортируется на чистом профиле с полным восстановлением прогресса (включая ошибки и попытки экзамена).
8. Импорт валидирует файл строгой store-валидацией; невалидный файл не меняет текущее состояние и даёт понятную человекочитаемую ошибку; валидный файл после подтверждения замещает состояние и персистится.
9. Кнопки экспорта/импорта размещены рядом с кнопкой сброса, имеют aria-label/титулы на русском в стиле существующей шапки.
10. Диалоги доступны с клавиатуры (фокус-ловушка, Esc, автофокус на безопасной кнопке), соответствуют touch/focus-паттернам приложения.

## Ожидания приёмки

- **AC-1 (из ТЗ-P1, дословно применимо к этому слайсу):** тап по «Сбросить прогресс» не удаляет данные без подтверждения; после подтверждения доступна «Вернуть» до конца сессии; экспортированный JSON импортируется на чистом профиле с полным восстановлением (e2e).
- Негативный сценарий подтверждения (e2e): открыть диалог, нажать «Отмена»/Esc — счётчики StatusStrip и localStorage-ключ прогресса не изменились.
- Негативный сценарий импорта (e2e): импорт битого JSON (не-JSON, чужая схема, неизвестная `version`) не меняет текущий прогресс и показывает понятную ошибку; после закрытия ошибки приложение полноценно работает.
- Undo-сценарий (e2e): сброс → «Вернуть» → ответы, ошибки и попытки экзамена восстановлены; счётчики StatusStrip совпадают с состоянием до сброса.
- A11y-проверка диалога: Esc закрывает, фокус заперт в диалоге, автофокус на безопасной («Отмена») кнопке — e2e и/или ручной чеклист с зафиксированным результатом.
- Существующий e2e-набор (`tests/e2e/app.spec.ts`, 59 тестов × 2 проекта Desktop+Pixel 7) зелёный; unit-набор `node --test` зелёный.
- Гейты `pnpm run quality:fast`, `pnpm run format:check`, `pnpm run preflight` зелёные; в PR записаны фактические свидетельства (verification evidence), а не только AI-резюме.
- В коде UI нет прямого обращения к localStorage-ключам прогресса — только публичный API `src/progressStore.ts`.

## Негативные сценарии (обязательные для feature memory)

- Случайный тап по RotateCcw без подтверждения ничего не удаляет.
- Импорт битого/чужого JSON не портит и не очищает текущий прогресс, даёт понятную ошибку (главный негативный сценарий цикла).
- Перезагрузка страницы после сброса, но до undo: снапшот в sessionStorage переживает reload той же вкладки — кнопка/путь «Вернуть» остаётся доступным (или Architect явно фиксирует иное поведение с обоснованием).
- sessionStorage недоступен (private mode/квота): сброс работает, пользователь предупреждён об отсутствии undo, приложение не падает.
- Двойное нажатие «Вернуть» не создаёт дубликатов записей.

## Допущения и default-ответы на открытые вопросы

Пользователь недоступен для Q&A; зафиксированы явные допущения. Architect может уточнить их в `spec.md` без изменения пользовательских гарантий; конфликт с гарантиями — блокер через Orchestrator.

- **A1. Схема подтверждения (ТЗ даёт выбор «текстовый ввод или двойное подтверждение»).** Default: двойное подтверждение (например, чекбокс «Я понимаю, что данные будут удалены» + активация кнопки удаления, либо двухшаговая кнопка), без текстового ввода — текстовый ввод неудобен на мобильном, а основной сценарий приложения мобильный. Текстовый ввод допустим, если Architect обоснует.
- **A2. Ключ снапшота undo.** Default: новый sessionStorage-ключ в существующем неймспейсе, например `cabadrive.progress.reset-undo.v1`; содержимое — строка `exportProgress()` (канонический v2). Точное имя — за Architect.
- **A3. Путь восстановления undo.** Default: восстановление через `dispatchProgress({ type: "importProgress", raw: snapshot })` — переиспользуем строгую валидацию и атомарность; отдельного «restore»-действия в store не добавляем без задокументированной причины (принцип Simplicity).
- **A4. Импорт тоже разрушителен.** Default: перед применением валидного импорта — подтверждение в том же ConfirmDialog (замещение текущего прогресса) и/или undo-снапшот текущего состояния по механизму FR-A2. Минимум — одно из двух; выбор за Architect.
- **A5. Имя экспортного файла.** Default: `cabadrive-progress-<YYYY-MM-DD>.json`; реализация — Blob + `URL.createObjectURL` + временный `<a download>` без новых зависимостей.
- **A6. Компонент диалога.** Default: один переиспользуемый `ConfirmDialog` на нативном `<dialog>` (`src/components/ConfirmDialog.tsx` — первый файл в `src/components/`), стилизация под существующие панели, без UI-библиотек — как предложено в ТЗ-P1 §6. Он же — задел для слайса 2 (FR-A5), но обобщать сверх нужд слайса 1 не требуется.
- **A7. Сообщения об ошибке импорта.** Default: человекочитаемый русский текст на базе события `importRejected` (не сырой console-вывод); детальная диагностика остаётся в существующих recovery-механизмах store.
- **A8. Расположение кнопок.** Default: экспорт/импорт — icon-кнопки рядом со сбросом в `app-header` (по FR-A3 «кнопки рядом со сбросом»); при тесноте на мобильном Architect может выбрать компактную группировку, сохранив touch-таргеты ≥42 px.
- **A9. Номера строк.** Все ссылки на строки в этом документе проверены на base `3fed47cc`; исполнитель обязан перепроверять их на своём HEAD.
