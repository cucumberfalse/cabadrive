### D-07 scheduling checkpoint requirements

1. Use the dedicated trusted wakeup workflow's ordinary GitHub Actions bot identity and least-privilege token, not `GITHUB_ACTOR` (which names the event sender), a native review bot, an owner token, or an arbitrary configured human. Validate server-returned author login/type and schema. Other authors' copied markers are not scheduler state. Multiple conflicting trusted checkpoints, malformed state, unexpected actor changes, and mismatching PR/repository/head/run/attempt identity fail closed with a visible diagnostic; do not select an attacker-preferred duplicate or overwrite a foreign comment.
2. Pin one canonical checkpoint comment ID per PR. Validate a strict versioned schema, full head, exact workflow run ID and run attempt, fingerprint syntax, and recognized scheduling state. Recompute the fingerprint independently from a sorted snapshot of trusted native signal IDs, full relevant bodies, actual server update/submission times, applicable thread-resolution state, expected full head, and selected backend. Exclude scheduler comments, gate failure notices, and review-request markers so writing the checkpoint cannot change its own input or clear findings. Structured summaries remain wakeup-only in that snapshot.
3. Direct native-event and AI Review completion-backstop handlers share the same per-PR serialization. Before claiming or rerunning, re-fetch the live PR/head, exact eligible workflow run/attempt, checkpoint, and native snapshot. A queued obsolete event must not mutate or rerun a new head. Runtime input verification still applies even if the workflow filter matched.
4. A pre-rerun checkpoint records a pending claim, not proof of dispatch or consumption. Derive accepted scheduling from GitHub's actual eligible run/attempt state. Suppression based on a consumed fingerprint requires proof that the corresponding exact-head target attempt started strictly after both the server-side checkpoint write time and the newest included signal update time. Equality at second precision is ambiguous: wait beyond the boundary for the claimed rerun or take one conservative requeue, then converge using the confirmed later attempt. A forged or later-edited checkpoint cannot retroactively attribute a prior run to a new snapshot. Do not update a successfully written claim merely to label it accepted if that destroys its server-side temporal proof; derive acceptance from run state, or preserve independently verifiable immutable write provenance.
5. If a crash or timeout occurs between checkpoint write and rerun request, pending state cannot suppress evaluation forever. Reconcile the run ID/attempt through a bounded API retry first. A network-uncertain mutation must not be blindly retried, because GitHub may already have accepted it. If acceptance still cannot be determined, stop with explicit uncertain-scheduling evidence instead of inventing success or creating duplicate reruns. A definitive denied/rejected request may record that state for a deliberate authorized retry; its own completion must not generate an automatic retry loop.
6. Include process/API tests for human marker forgery, conflicting bot checkpoints, tampered schema/head/attempt/hash, a prior run referenced by a later checkpoint, same-second updates, active/completion boundaries, queued stale events, crash before POST, accepted POST with lost response, delayed API visibility, explicit denied retry, and unchanged repeated completion. A checkpoint can only coordinate a real gate attempt; the gate independently re-fetches native evidence and unresolved findings before any pass.

Validate the observed JSON root and both `code_review`/`security_review` objects, their exact expected fields, full 40-hex-or-null commit identity, nullable booleans, nullable/nonempty status, and coherent combinations. An empty slot has all fields null; `completed` requires boolean verdict fields; unresolved true requires any-findings true. Unknown/malformed/duplicated fields, markers, status shapes, or contradictory content never become positive or silently neutral evidence.
- Only an explicit full current-head slot can assert its negative/unfinished state. A valid explicitly other-head summary cannot veto current-head evidence. - Inspect positive/negative receipt semantics, blocking priorities, duplicate/conflicting markers, and mixed receipt-plus-summary content before the generic summary-only path. ### D-12 fork-native event signal bridge with trusted permissions

Independent review identified a required actual-fork execution defect: `pull_request_review` and `pull_request_review_comment` workflows use the PR merge ref, and a fork's GITHUB_TOKEN is read-only. Combining them with privileged issue-comment/completion events in one YAML does not give those review-event runs rerun/checkpoint authority, even when scripts are checked out from main. Orchestrator verified these source/token semantics against the official [workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) documentation. Accepted as a required T-06/T-07 follow-up because this feature's publication uses a fork.

Use a minimal unprivileged native-review signal workflow for formal/inline events, plus a separately trusted-default-branch `workflow_run: completed` bridge to the existing wakeup router. The signal job requires no checkout, repository script execution, secrets, write permissions, artifact, or payload program. Its completion is only a scheduling hint; it cannot approve a review or supply executable/privileged data. A source PR may alter its unprivileged workflow, so the receiver must distrust its content, logs, artifacts, title, success, and claims.

The trusted receiver validates the expected source workflow identity/path and permitted event kinds through GitHub API state, then independently fetches native trusted evidence and the eligible current-head AI Review run. Preserve the direct trusted-default `issue_comment` route and the AI Review completion backstop. Give only the receiver's trusted job the explicit actions/issues permissions needed for real rerun/checkpoint operations. Never execute the source PR checkout or artifacts with that token; no `pull_request_target` PR-code execution is introduced.

Verify source-run-to-PR association using server metadata and fresh PR state. Associated-PR arrays may be absent on fork workflow-run payloads; do not assume a nonempty array or silently drop formal-only late results. A fallback must establish repository/branch/commit/PR correspondence through API-backed identity and reject ambiguity. Review-event merge refs and merge SHAs must not be blindly equated with the raw PR head: accept only a verified raw-head association, or a verified merge-commit relationship to that exact current raw head and base. Untrusted source metadata can be a candidate hint only, never the proof. Revalidate the immutable full head immediately before any checkpoint or rerun, and fail closed with a diagnostic if association cannot be proven.

Tests execute the separate workflow/receiver contracts: real fork read-only signal, formal-only late result after terminal AI gate, inline event while active, successful and failed signal completion as hints, empty associated-PR arrays with verified fallback, raw-versus-merge head distinction, forged name/title/artifact/PR metadata, wrong workflow/repository/PR/head, new push, required current-head check association, and unchanged duplicate completion convergence. Record remote approval/permission or absent-default-workflow limitations honestly during bootstrap.
