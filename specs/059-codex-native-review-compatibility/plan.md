### D-07 scheduling checkpoint requirements

1. Recompute the fingerprint independently from a sorted snapshot of trusted native signal IDs, full relevant bodies, actual server update/submission times, applicable thread-resolution state, expected full head, and selected backend. Exclude scheduler comments, gate failure notices, and review-request markers so writing the checkpoint cannot change its own input or clear findings. Structured summaries remain wakeup-only in that snapshot.
3. Direct native-event and AI Review completion-backstop handlers share the same per-PR serialization. Before claiming or rerunning, re-fetch the live PR/head, exact eligible workflow run/attempt, checkpoint, and native snapshot. A queued obsolete event must not mutate or rerun a new head. 4. A pre-rerun checkpoint records a pending claim, not proof of dispatch or consumption. Derive accepted scheduling from GitHub's actual eligible run/attempt state. Suppression based on a consumed fingerprint requires proof that the corresponding exact-head target attempt started strictly after both the server-side checkpoint write time and the newest included signal update time. Equality at second precision is ambiguous: wait beyond the boundary before posting from a retryable claim. Once a checkpoint is `posting`, no conservative requeue is allowed until its previous POST is proven settled under D-09; an advanced attempt without strict timing proof is still uncertain. A forged or later-edited checkpoint cannot retroactively attribute a prior run to a new snapshot. Do not update a successfully written claim merely to label it accepted if that destroys its server-side temporal proof; derive acceptance from run state, or preserve independently verifiable immutable write provenance.
5. If a crash or timeout occurs between checkpoint write and rerun request, pending state cannot suppress evaluation forever. Reconcile the run ID/attempt through a bounded API retry first.
