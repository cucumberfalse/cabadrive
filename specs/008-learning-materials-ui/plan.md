Implement one conservative UI slice that exposes the existing `006` topic study guide data inside the current static React app. The slice should add a new top-level materials view, render topic list/detail content from structured JSON, join guide ticket references to canonical question data, preserve draft/unofficial/fallback clarity, and verify the flow with focused tests and preflight.

This Architect pass only creates feature memory. It does not edit product code, tests, durable docs, content, package files, `006` feature memory, git config, commits, pushes, or PRs.

## Architect Decisions

### Treat 008 As The UI Slice For 006 Slice F

`006` left Slice F UI tasks T061-T067 open. This feature should implement that UI surface as a standalone `008` PR slice and record in `008` process memory that it closes/cross-references those tasks. Implementation must not edit `specs/006-topic-study-guide/*` unless a future Architect explicitly changes that boundary.

### Preserve The Existing CABA/RF Guide

The old `CABA/RF` guide remains a separate navigation entry for this slice. The new materials section should not replace it, because the two surfaces answer different learner questions:

- `CABA/RF`: compact contrast guide.
- `Материалы`: topic study guide generated by `006`.

### Use A New React View

Use the existing local `View` union and state-driven navigation pattern. Add a new value such as `materials` or `topicGuide`, plus a new component such as `TopicGuideView`. Do not add a router unless implementation discovers an existing routing pattern or a concrete need.

### Use The Existing Data Boundary

Import the topic guide JSON through `src/data/content.ts` and add explicit TypeScript types there or in a nearby local module. Avoid large generic schema frameworks for this UI slice.

### Join Canonical Questions At Render Time

Guide ticket blocks should reference `questionId` and `answerId`. The UI must render Spanish question text, answer options, correct answer, source status, and local images from canonical question data. The guide's `tickets[].answerExplanations` provides Russian per-answer explanations.

### Draft Status Is Visible, Not Blocking

The guide is currently `draft`, but the user asked to expose the existing materials. Therefore the UI may show draft material in the app if it clearly labels it as draft/incomplete and unofficial. Do not mark it published or complete.

### Compact Learner Source Context Only

The UI should show compact status text such as "неофициальный учебный материал" and fallback question status. It should not render raw official-document archive details or source-trace internals unless implementation identifies a small learner-friendly status affordance.

## Implementation Strategy

1. Add topic guide imports and types.
2. Create small helpers for:
   - `questionById`;
   - answer explanation lookup by `answerId`;
   - status label rendering for `draft` and `unofficial_learning_aid`;
   - optional filtering to topics with material/tickets if needed.
3. Add a new top navigation tab using a short Russian label, preferred `Материалы`.
4. Implement `TopicGuideView` with list/detail state:
   - default to topic list plus first/selected topic detail, or list with a clear selected detail pane;
   - keep mobile-friendly scan order;
   - avoid nested cards inside cards.
5. Render topic list in guide order from `topicGuide.topics`.
6. Render topic detail:
   - title and summary;
   - draft/unofficial/fallback status;
   - `learningMaterialRu`;
   - `practicalReasoningRu` when present;
   - `spanishTerms`;
   - ticket blocks;
   - `trapNotes` when present.
7. Render ticket blocks:
   - locate canonical question by `questionId`;
   - render Spanish question text;
   - render local image from canonical `question.image.localPath` when present;
   - render answer options in canonical order;
   - mark the correct answer;
   - attach the matching Russian explanation from topic guide `answerExplanations`;
   - show a non-crashing missing-reference state for missing question/answer data.
8. Add focused tests:
   - e2e for top nav reachability;
   - e2e for topic detail rendering and status labels;
   - e2e for image ticket rendering;
   - e2e or unit/DOM evidence for a dual-topic ticket full render when data supports it;
   - unit tests for join/status helpers if helpers are separated.
9. Update durable docs only if the implemented navigation behavior changes documented learning flows.
10. Run validation/preflight and record evidence in `tasks.md`.

## UI Guidance For Implementation

- The first screen after clicking `Материалы` should be the usable materials UI, not an explanatory landing page.
- Use existing app typography, buttons, panels, and status styles where possible.
- Keep text sizes appropriate for a work-focused trainer surface, not a marketing hero.
- Use icon+text for the new nav button, preferably an existing `lucide-react` icon such as `Library`, `NotebookTabs`, `BookMarked`, or `BookOpenCheck` if available.
- Use stable layout constraints for topic list/detail and ticket blocks so long Spanish/Russian text does not overflow on mobile.
- Avoid exposing raw JSON field names like `unofficial_learning_aid` directly as learner text.
- Do not create a separate docs site or PDF-like viewer.

## Risks And Mitigations

- Risk: Learners mistake draft materials for final official guidance.
  - Mitigation: show draft/incomplete and unofficial-learning-aid labels in the materials section.
- Risk: UI duplicates canonical Spanish ticket data and drifts from practice mode.
  - Mitigation: render canonical question and answer data by ID.
- Risk: Existing navigation becomes crowded.
  - Mitigation: use a short label and existing responsive tab styles; adjust CSS only as needed for wrapping.
- Risk: Topic pages become long on mobile.
  - Mitigation: use list/detail selection and scannable sections; only add pagination/collapse if evidence shows the current layout is unwieldy.
- Risk: Dual-topic physical rendering is hard to prove if no ready dual-ticket blocks exist.
  - Mitigation: inspect existing guide data during implementation and choose a dual assigned ticket with rendered ticket data; if no suitable data exists, record the blocker and test the renderer with the closest available fixture/helper.
- Risk: Source-trace/official-document data leaks into learner UI as noisy archive internals.
  - Mitigation: render compact status text only.
