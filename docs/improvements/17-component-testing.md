## 1. Контекст и проблема

Тестовая система обширна (31 файл, ~502 test()-вызова + 5348 строк e2e), но **ни одного компонентного React-теста нет**: vitest/jest/@testing-library отсутствуют в devDependencies. App.tsx (4108 строк UI-логики) проверяется только «сверху» (e2e, медленно и крупно) и «сбоку» — хрупкими регэксп-тестами по исходному тексту (tests/manual-ticket-placement.test.mjs:441-494 матчит appSource; аналогично ai-review-workflow, docker-runtime): безобидный рефакторинг их ломает, а семантическую регрессию с другой формулировкой они пропустят. Прямых unit-тестов нет у src/search.ts, src/storage.ts, src/difficulty.tsx. Чистая логика (domain.ts) тестируется через ts.transpileModule + data:-URI — работает, но паттерн не масштабируется на компоненты. Покрытие не измеряется.

## 2. Цели

Поведение ключевых компонентов проверяется быстрыми изолированными тестами; регэксп-тесты по исходникам вытеснены; порог покрытия ключевых модулей закреплён.

## 3. Требования

- FR-1: Vitest + @testing-library/react + jsdom: `vitest.config.ts` с окружением jsdom для `src/**/*.test.tsx`; существующие node --test контент-гейты НЕ трогаются (два раннера сосуществуют: `pnpm test` = node --test + vitest).
- FR-2: Стартовый пакет компонентных тестов: QuestionCard (выбор ответа, verно/неверно, перевод, disabled после ответа), ExamView-таймер (fake timers: старт/дедлайн/finish один раз), MistakesView (закрытие ошибок — после [ТЗ-P1](./priority/01-usability.md) FR-V1), ConfirmDialog, StatusStrip.
- FR-3: Unit: search.ts (диакритика, темы — совместно с [ТЗ-09](./09-search-layer-memoization.md)), storage.ts (миграции, кап — совместно с [ТЗ-06](./06-progress-store.md)), difficulty.tsx, router.ts.
- FR-4: Coverage (v8-провайдер vitest) с порогом для src/: statements ≥ 60 % стартово, повышение по мере декомпозиции; отчёт в CI-артефакт.
- FR-5: Демонтаж регэксп-тестов по исходникам: каждый заменяется компонентным/поведенческим эквивалентом (инвентаризация в первом PR; правило — новый регэксп-тест по src не добавляется).
- NFR-1: Компонентный набор ≤ 30 с локально.

## 4. План

- [ ] 1. Инфраструктура vitest+RTL; первый тест (QuestionCard) как образец паттернов (рендер с фикстурным вопросом)
- [ ] 2. Пакет FR-2 (лучше после выноса компонентов — ТЗ-04 этап 3; допустимо и до, импортом из App.tsx невозможно — компоненты не экспортированы, поэтому согласование с ТЗ-04 обязательно)
- [ ] 3. Unit FR-3
- [ ] 4. Coverage-порог в CI; инвентаризация и замена регэксп-тестов

## 5. Критерии приёмки

- AC-1: `pnpm test` гоняет оба раннера; vitest-набор зелёный.
- AC-2: Намеренная поломка логики выбора ответа ловится компонентным тестом (мутационная проверка на ревью).
- AC-3: Coverage-гейт активен; отчёт в CI.
- AC-4: Количество регэксп-матчей по «src/App.tsx» в tests/ уменьшено до 0 (по завершении вместе с ТЗ-04).

## 6. Риски и меры

| Риск | Вероятн. | Влияние | Мера |
|---|---|---|---|
| Компоненты не экспортированы из App.tsx | Гарантированно | Блокер FR-2 | Последовательность с ТЗ-04: тесты пишутся на вынесенные модули |
| Два тест-раннера путают агентов | Средняя | DX | Правило в AGENTS.md: контент-гейты — node --test, UI — vitest |
| React 19 + RTL совместимость | Низкая | Затык инфраструктуры | @testing-library/react ≥ 16 поддерживает React 19 |
