## 1. Контекст и проблема

Прогресс пользователя поднят в App (App.tsx:3974) и прокидывается пропсами progress/setProgress в три вью; персистентность размазана: паттерн «собери next → setProgress(next) → saveProgress(next)» повторён 4 раза — LearnView.record (App.tsx:744-746), toggleDifficult (App.tsx:752-757), ExamView.finish (App.tsx:919-921), MistakesView.record (App.tsx:968-971). Забытый saveProgress в новом месте = тихая потеря данных.

[src/storage.ts](../../src/storage.ts) не имеет ни версии схемы/миграций (ключ `cabadrive.progress.v1` зашит, storage.ts:3), ни ограничения размера: `answers` растёт неограниченно — каждый клик по ответу делает append (App.tsx:744, 892→919, 969); квота localStorage (~5 МБ) достижима при активном использовании. `loadProgress` валидирует только `Array.isArray` на верхнем уровне (storage.ts:30-34) — повреждённые вложенные записи проходят в рантайм.

## 2. Цели

1. Одна точка записи прогресса; невозможно забыть персист.
2. Схема версионируется; будущие изменения формата не теряют данные пользователей.
3. История ответов ограничена; переполнение квоты обрабатывается.

## 3. Не-цели

- Внешняя state-библиотека (Redux/Zustand) — объём состояния мал, достаточно useSyncExternalStore.
- Синхронизация между устройствами / бэкенд.
- Перенос в IndexedDB (отдельно оценивается в [ТЗ-15](./15-ios-storage-persistence.md)).

## 4. Требования

- FR-1: `src/progressStore.ts`: reducer с действиями `recordAnswer`, `toggleDifficult`, `finishExam`, `reset`, `importProgress`; автоперсист — подписка на изменения в единственной точке; хук `useProgress()` на useSyncExternalStore.
- FR-2: Сериализованный объект получает поле `version: 2` и durable-агрегат `prunedAnswerStats`: упорядоченный массив записей `{ questionId, wrong, lastPrunedAnswer, firstSeenOrder }` для каждого вопроса, хотя бы раз попавшего в удалённый префикс. `wrong` — накопленное число неправильных ответов только из уже удалённых записей; `lastPrunedAnswer` — последняя удалённая запись этого вопроса со всеми полями `ProgressAnswer`; `firstSeenOrder` — стабильный порядок первого появления, нужный для сохранения порядка при равном `wrong`. Миграция v1→v2 сначала валидирует текущий формат, сохраняет существующие `answers`, `difficultQuestionIds` и `examAttempts` без потерь и создаёт пустой агрегат; если v1-история уже длиннее капа, общий алгоритм FR-3 затем переносит лишний префикс в агрегат. Сырая v1-строка резервируется до записи v2. Вложенные записи обоих форматов валидируются: локально повреждённые/дублированные aggregate-записи не используются для выдумывания статистики, сохраняются в диагностическом backup, дают `console.warn`/событие восстановления, а валидный retained suffix продолжает загружаться; невалидный импорт отклоняется целиком.
- FR-3: `answers` хранит хронологический retained suffix не длиннее `N=5000`. Единая чистая операция pruning берёт только новый удаляемый префикс и ровно один раз добавляет каждый его неправильный ответ в `prunedAnswerStats`, обновляет `lastPrunedAnswer` каждым удалённым ответом и назначает новый `firstSeenOrder` при первом попадании вопроса в агрегат; уже агрегированные записи повторно не сворачиваются. Selector сохраняет точную семантику `mistakesFromHistory` из `src/domain.ts:70-82`: начинает `Map` с aggregate-записей в `firstSeenOrder`, затем хронологически применяет retained suffix, складывает `aggregate.wrong + retained wrong` ровно по одному разу, выбирает последнюю retained запись как `last`, а при её отсутствии — `lastPrunedAnswer`, фильтрует только вопросы с `wrong > 0` и стабильно сортирует по убыванию `wrong`. Поэтому вопрос, существующий только в удалённом префиксе, остаётся в результате, а при равных счётчиках сохраняется исходный порядок первого появления.
- FR-4: `saveProgress` оборачивается в `try/catch`. Перед первой записью применяется кап FR-3. При `QuotaExceededError` удаляется очередной непересекающийся старейший фрагмент retained `answers` (начиная с половины), он один раз переносится тем же pruning-helper в агрегат, и запись повторяется; каждый следующий quota-retry работает уже со следующим retained prefix, поэтому повторное/последовательное усечение не удваивает счётчики. Если квота не освобождается после исчерпания retained history, store сохраняет консистентное состояние в памяти и поднимает событие для UI-уведомления/экспорта вместо тихой потери данных.
- FR-5: Экспорт/импорт прогресса (JSON-файл) — API store, UI-часть в [ТЗ-P1](./priority/01-usability.md) FR-A3. Экспорт содержит канонический полный v2 (`answers` + `prunedAnswerStats`), импорт атомарно валидирует version, aggregate invariants, уникальность `questionId`/`firstSeenOrder` и все вложенные записи, применяет общий cap/pruning и только затем заменяет store; export→import→export даёт эквивалентное каноническое состояние и тот же selector result. `reset` очищает retained history и агрегат вместе с остальным прогрессом.
- NFR-1: Поведение вью не меняется (тот же формат данных для компонентов); e2e зелёные.

## 6. Критерии приёмки

- AC-1: grep `saveProgress(` по src — единственный вызов внутри progressStore.
- AC-2: Существующий v1 fixture из прод-localStorage мигрирует с неизменными `answers`, `difficultQuestionIds` и `examAttempts` и изначально пустым `prunedAnswerStats`; повторная загрузка v2 идемпотентна.
- AC-3: Для полной истории из 6000 ответов `mistakesFromHistory(full)` deep-equal результату v2 selector после капа до 5000 retained записей: совпадают cumulative `wrong`, порядок (включая равные счётчики) и все поля `last`; отдельный неправильно отвеченный вопрос только из удалённого префикса остаётся в результате через `lastPrunedAnswer`.
- AC-4: Последовательные превышения `N=5000` и повторные pruning-вызовы переносят только новый префикс: aggregate+retained учитывают каждый неправильный ответ ровно один раз и сохраняют последнюю retained запись как `last`.
- AC-5: Замоканный `QuotaExceededError` требует нескольких усечений; после каждого retry selector остаётся эквивалентен полной до усечения истории, pruned-only вопрос сохраняется, счётчики не удваиваются, а исчерпание retained history поднимает контролируемое событие и не роняет приложение.
- AC-6: Валидный v2 export/import round-trip сохраняет aggregate, retained suffix, порядок и selector result; неизвестная version, duplicate/invalid aggregate, несовпадающий `lastPrunedAnswer.questionId` или битая вложенная запись отклоняют импорт атомарно.
- AC-7: `reset` очищает `answers` и `prunedAnswerStats`; повреждённый локальный aggregate не роняет загрузку, не создаёт ложные mistakes и оставляет диагностируемый backup/warning при сохранённом валидном suffix.
- AC-8: e2e-набор зелёный; существующие view получают прежнюю форму `{ questionId, wrong, last }` без изменения пользовательского поведения.

## 7. Риски и меры

| Риск | Вероятн. | Влияние | Мера |
|---|---|---|---|
| Ошибка миграции портит данные пользователей | Низкая | Критично | Бэкап сырой строки в `cabadrive.progress.v1.backup` перед миграцией; фикстурные тесты |
| Повторный cap/quota trim дважды учитывает удалённые ответы | Средняя | Высокое | Один pruning-helper принимает только новый retained prefix; full-vs-capped, repeated-trim и multi-QuotaExceeded fixtures сравнивают selector deep-equal |
| Повреждённый aggregate или импорт создаёт ложные счётчики | Низкая | Высокое | Строгие per-entry/duplicate/order/invariant проверки; локальный backup+warning без выдумывания данных, атомарный reject импорта |
| Aggregate сам не помещается после исчерпания retained history | Низкая | Среднее | Не удалять накопленные счётчики молча; сохранить консистентное in-memory состояние, показать уведомление и предложить экспорт |
| Расхождение с параллельными правками вью (ТЗ-P1) | Средняя | Конфликты | Store — первым; слайсы ТЗ-P1 используют его API |
