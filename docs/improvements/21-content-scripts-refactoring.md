## 1. Контекст и проблема

~35 ESM-скриптов в scripts/ накопили системные проблемы (проверено по исходникам):

1. **Дублированные критичные утилиты**: canonicalJson/sha256Canonical реализованы отдельно в content-shards.mjs и content-image-metadata.mjs; readJson/writeJson, isPlainObject, испанские regex-словари — множатся по скриптам. Расхождение любой копии canonicalJson тихо ломает все fingerprint/freshness-проверки (byte-exact сравнение индексов).
2. **Монолиты с данными в коде**: manual-sign-inventory.mjs — 4627 строк (209 КБ) с зашитым инвентарём знаков; content-manual-vehiculo-4ruedas.mjs ~2000 строк. Правка контента = правка валидатора; высокий риск merge-конфликтов.
3. **Смешение корней**: часть скриптов резолвит пути от process.cwd(), часть — от import.meta.url; запуск не из корня репозитория даёт ложные «файл отсутствует».
4. **Захардкоженные reviewedAt/reviewer/GENERATED_AT** в генераторах: перегенерация подделывает старые даты ревью; byte-exact evidence провоцирует запуск с --write без реального ревью.
5. Валидация прод-контента зависит от specs/: manual-sign-inventory.mjs читает evidence из specs/037-*/evidence/ — перемещение/архивация specs сломает validate:content.

## 2. Цели

Одна реализация каждой критичной утилиты; данные инвентарей — в content/, не в коде; скрипты работают из любого cwd; метаданные ревью честные.

## 3. Требования

- FR-1: `scripts/lib/` (canonical-json.mjs, hashing.mjs, fs-json.mjs, repo-root.mjs): все скрипты переводятся на общие модули; дубликаты удаляются. repo-root.mjs — резолв корня от import.meta.url (поиск package.json вверх), полный отказ от cwd-зависимости.
- FR-2: Инвентарь знаков из manual-sign-inventory.mjs выносится в `content/manual-signs/inventory.json`; скрипт становится валидатором ≤ 500 строк. Аналогично оценить content-manual-vehiculo-4ruedas.mjs.
- FR-3: Метаданные ревью отделяются от генерируемого содержимого: generated-файлы не содержат дат/ревьюеров; reviewed-статусы живут в отдельном ledger-файле, обновляемом осознанно (не --write генератора).
- FR-4: Зависимость validate:content от specs/ устраняется: используемые evidence переносятся в content/validation с указанием происхождения.
- FR-5: Регрессионная сетка: byte-exact сравнение всех генерируемых индексов/evidence до и после каждого шага (git diff пуст, кроме осознанных изменений).
- NFR-1: Ни одно поведение валидации не ослабляется (те же ошибки на тех же нарушениях — негативные фикстуры до рефакторинга).

## 4. План

- [ ] 1. scripts/lib + перевод двух самых критичных потребителей (content-shards, content-image-metadata) + негативные фикстуры
- [ ] 2. Перевод остальных скриптов на lib; repo-root везде
- [ ] 3. FR-2 (вынос инвентаря знаков)
- [ ] 4. FR-3 + FR-4 (ledger ревью; независимость от specs/)

## 5. Критерии приёмки

- AC-1: grep canonicalJson — одна реализация в scripts/lib.
- AC-2: Запуск validate:content из подкаталога работает (тест из tmp-cwd).
- AC-3: manual-sign-inventory.mjs ≤ 500 строк; инвентарь — JSON в content/.
- AC-4: Перегенерация не меняет reviewedAt существующих записей (негативный тест).
- AC-5: Полный validate:content зелёный; git diff генерируемых файлов пуст после чистого прогона.

## 6. Риски и меры

| Риск | Вероятн. | Влияние | Мера |
|---|---|---|---|
| Тонкое изменение canonicalJson при унификации | Средняя | Ломаются все пины | Байтовое сравнение выводов старой/новой реализации на всём content/ до слияния |
| Большой объём механических правок | Высокая | Затяжка | Строго по одному скрипту на PR |
